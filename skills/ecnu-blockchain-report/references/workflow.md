# 制作与验收流程

本流程来自HotRevoke的11.13汇报修订实践，用于保留可重复的制作方法。它不要求每个任务固定页数，也不要求复制同一实验或同一图。

仓库脚本分别负责构建（`scripts/build_report.py`）、结构检查（`scripts/validate_report.py`）与导出预览/PDF（`scripts/render_report.py`）。在仓库根运行；安装为个人技能后，在该技能根运行。先用各脚本的 `--help` 查看实际参数。构建不等于已经渲染，渲染成功也不等于完成逐页视觉检查。

## 1. 建立明确输入

先找到用户实际保留的模板、待改PPT、当前论文和本次数据。将原PPT/PDF备份到工作区的私有构建目录。记录输入文件的相对路径与哈希，分开管理两类资料：真正参与构建的模板、内容和数据，以及只用于审阅的论文或代码。后者不应成为下载模板后无法重建的隐性依赖。

通过PPTX中的演示顺序读取幻灯片，不依赖`slide1.xml`之类的文件编号推断页序。渲染参考页，查看封面、正文、目标、反思和计划的真实布局。只看母版名称或缩略图不足以决定字号、留白与连线。

已有手工修改优先保留。不要直接运行旧生成脚本覆盖用户的最新版本；先比较脚本、PPT与当前论文的差异。若内容发生冲突，明确指出冲突所在，保存原稿，依据用户的最新要求处理。

## 2. 写出听众能跟上的正文

先用一段话描述本周变化，再给每页确定一个目的。对研究型周报，常见的连续叙事是：具体问题、已有方法、当前方案、关键判断或算法、实验结果与代价。用户已有结构时在其基础上调整，不机械套用这一顺序。

以一个小例子连接多个技术页。例子中的人物、对象、序号、状态和条件应保持一致。解释架构时跟着一条请求走：输入如何进入、数据放在哪里、何时可以回答、后续维护做什么。解释算法时说明判断原因及失败情况，而不是仅把伪代码截图贴在页上。

为每页保存标题、核心内容、来源、备注和建议时长。备注进一步解释术语、测量边界、局限与可能提问，帮助汇报者学习；备注不能弥补正文关键判断条件的缺失。

目标、反思和计划形成对应关系。目标说明这阶段要解决什么；反思说明这周理解发生了什么变化；下周计划说明尚未回答的问题及准备怎样验证。避免三页重复列同一批口号。

## 3. 制作可编辑页面

复用模板的画幅、学校标志、字体角色和分隔线。把内容放进合适的原生文本框、表格、图形或图表；复制模板时保留必要的主题、母版、媒体和关系文件。

先确定图的整体区域和阅读方向，再放模块与连线。模块名称靠近图形；条件标签靠近分支；回线经过空白处。通过临时移动模块检查连接关系，尤其注意原本应当独立推进的过程是否被画成必须等待的串行步骤。

保留真实图表的嵌入工作簿和公式。若数字缓存与工作簿仅有浮点序列化末位差异，先核对来源，再将缓存刷新到原单元格并记录变化；不得任意替换整个工作簿。若数据本身不同，先解决来源冲突再作图。

## 4. 将事实和版式分开检查

内容检查核对叙事、术语、算法分支和图中职责。数据检查核对原始统计、条件、单位、分母、误差线、失败项和结论范围。独立审查有助于发现作者已经习惯而读者看不懂的表达，但不替代主作者确认。

结构检查可验证PPTX关系完整、幻灯片数、原生图表数、工作簿引用、形状ID和连线端点。文本边界检查能发现部分溢出，但无法证明视觉效果正确。使用哪个应用导出、实际检查哪些项目，应在记录中写清楚。

将最终PPTX渲染成逐页图片，以实际阅读尺寸逐张查看；缩略总览只用于检查全稿节奏。重点检查正文与图注的距离、表格换行、图例、轴标题、单位、箭头方向、页码、字体回退、图片裁切。修正后再渲染受影响页，检查整个成品没有意外变化。

在临时副本中进行代表性的编辑、移动、保存和重新打开测试，最终版保留设计好的布局。PDF来自已经保存的最终PPTX。重建或换用其他软件后，旧视觉验收记录不能自动延用。

## 5. 交付与复用

修改现有周报时，把验收后的文件更新回原有入口，备份放在非交付目录。新周按用户的日期／周数规则创建一处明确入口。正式目录提供PPTX、PDF（需要时）、讲稿、内容配置及重建说明；预览、日志和临时副本独立存放。

记录构建所用输入及最终文件哈希。区分实验日期与汇报版本日期，注明本次是否重跑实验。发布前在缺少本机私有目录的隔离位置检验重建能力；不能依赖绝对路径、未提交的论文、密钥或插件缓存才能成功。

用户授权推送时，确认提交只包含本次成果及必要依赖，完成普通提交和推送，并核对远程提交。没有请求的新实验、邮件、定时任务不随模板复用而自动开展。
